Azure SRE Agent · Companion

Working across the boundary:
Palo Alto, F5 & other third-party platforms

Azure SRE Agent is hosted in Azure, but it is not limited to Azure-native data. How far it can help with a third-party platform depends on the telemetry and operational interfaces that platform exposes to the agent.

Where the agent's reach ends today

Native visibility stops at the third-party boundary until you connect telemetry or an API.

✔ Azure side — visible now

  • VMs, NICs, VNets, NSGs, routes, DNS
  • Load Balancer, App Gateway, Azure Firewall, Private Link
  • Azure Monitor, Log Analytics, App Insights, Activity Log
  • Deployments, resource health, change attribution
Boundary

✱ Inside Palo Alto / F5 — needs a connection

  • Live firewall policy & security rules
  • F5 virtual servers, pools, members, monitors
  • Session, threat, and traffic-management state
  • Vendor configuration history & diagnostics

What SRE Agent can do natively

No vendor integration required — it investigates the Azure side of the problem.

Built-in
🧭

Inspect Azure network path

VMs, NICs, VNets, NSGs, user-defined routes, Load Balancer, App Gateway, Azure Firewall, Private Link, and DNS.

Built-in
📈

Query Azure telemetry

Azure Monitor, Log Analytics, Application Insights, Activity Logs, and resource health for symptoms and recent changes.

Built-in
🔗

Correlate impact

Tie an outage to an Azure deployment, route change, security-rule change, unhealthy backend, or infrastructure event.

Built-in
🧩

Validate the expected path

Check whether Azure config and reachability match the intended traffic flow through a Palo Alto firewall or F5 device.

Built-in
🚨

Receive forwarded incidents

Alerts routed via Azure Monitor, PagerDuty, or ServiceNow — including ones raised by the vendor platform.

⛔

The limit

Without vendor telemetry or an API, it sees evidence up to the boundary — not what happened inside the product.

What it can dig up from third-party logs

Send Palo Alto / F5 logs to Log Analytics (or a queryable connector) and the agent can correlate them.

From logs
🔎

Session outcomes

Allowed, denied, dropped, reset, timed-out, or threat-blocked sessions.

From logs
🧾

Per-request detail

Source, destination, port, protocol, policy/rule, virtual server, pool, member, action, and recorded reason.

From logs
🕰️

Incident timelines

Compare before/after a change and pinpoint the first relevant failure in the sequence.

From logs
📊

Cross-signal correlation

Line up firewall / load-balancer events with Azure metrics, app exceptions, backend health, DNS, and Activity Logs.

From logs
🎯

Pattern detection

Repeated deny patterns, unhealthy members, traffic imbalance, TLS/cert failures, and capacity pressure — when the fields exist.

From logs
📌

Scope & next step

Estimate affected apps, endpoints, clients, regions, and time windows, then recommend the next diagnostic move with evidence.

Logs = observability, not control. The agent reports only the fields and history the source retains. Ingestion delay, parsing quality, sampling, clock skew, and missing correlation IDs limit results. Logs alone usually can't fetch live config, run a vendor diagnostic, or safely change a policy or pool member.

How the agent connects to a vendor platform

The connection determines what the agent can observe, query, or change.

Azure SRE Agent does not automatically gain access to Palo Alto, F5, or another vendor platform. You deliberately provide one of these integration paths, along with identity and network access.

Pattern 1 Telemetry only
Vendor logs → Log Analytics / Kusto → Agent
Agent can

Correlate traffic, threat, health, and Azure signals during an investigation.

Boundary

Historical, read-only visibility; no live configuration queries or vendor-side changes.

Pattern 2 Direct tools
Agent → MCP connector → Vendor API
Agent can

Inspect live policy, topology, sessions, and health through selected vendor operations.

Boundary

The connector's tools and vendor identity define exactly which queries or actions are available.

Pattern 3 Governed bridge
Agent → Function / Logic App / APIM → Vendor API
Agent can

Invoke approved workflows such as collecting diagnostics or making a narrow remediation.

Boundary

The bridge enforces validation, allow-listed actions, approvals, audit, and outcome checks.

Key distinction: Logs let the agent observe. An MCP connector lets it interact. A governed bridge lets it execute approved workflows behind enterprise controls.
↗

Recommended maturity path

Grow capability in stages; keep investigation credentials separate from remediation credentials.

Stage 1

Azure-side investigation

Reader access to Azure resources & telemetry. Correlate up to the vendor boundary.

Stage 2

Third-party log correlation

Ingest Palo Alto / F5 logs into Log Analytics for cross-signal analysis.

Stage 3

Read-only API access

Inspect live policy, topology, and health via vendor APIs or an MCP connector.

Stage 4

Scoped writes · Review mode

Narrow, allow-listed actions with approval, rollback, and verification for every change.

Practical rule: Azure SRE Agent can work across a third-party boundary only to the extent that it has authenticated access, network reachability, suitable tools, and reliable data from that system.
